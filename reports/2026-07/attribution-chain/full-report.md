## 一、背景与问题

### 1.1 Multi-Agent 编队的信任悖论

Multi-Agent 编队正从概念走向工程化落地。但一个根本问题尚未解决：

> A Agent 说"代码审过了" → B Agent 基于此部署 → C Agent 基于此验证
>
> **你凭什么信 A？**

传统认证机制只能回答"你是谁"，无法回答"你做的事可信任吗"。在 Agent 场景下，身份可信 ≠ 行为可信，行为可信 ≠ 决策可解释。

### 1.2 已有方案的不足

| 方案 | 能力 | 局限 |
|------|------|------|
| 行为审计（事件日志） | 记录"做了什么" | 无法回答"为什么这么做" |
| 动机审计（试图追问意图） | 理论上最完整 | LLM 无自我意识，动机不可观测，本质是哲学问题 |
| 沙箱隔离（Project Perception 方案） | 阻断越狱传播 | 无法区分"坏 Agent"和"被误导的 Agent" |

### 1.3 核心洞察

**动机不可知，但归因可追溯。**

法官判案不需要知道罪犯心里的真实想法——只需要证据链能证明他做了什么、基于什么做了这个决定。

同理，Agent 信任体系的工程解不在"动机审计"，而在**"归因链"**——每个 Agent 决策都附带一条可追溯的决策溯源记录。

## 二、归因链设计

### 2.1 核心概念

每个 Agent 在做出决策时，必须同时输出一个**决策溯源 JSON**，包含：

1. **决策结果** — 它做了什么
2. **输入溯源** — 它基于什么输入做了这个决定（每条输入附带影响权重）
3. **签名** — 确保链上各环节不可篡改

### 2.2 决策溯源 JSON 格式（草案）

```json
{
  "decision_id": "uuid-v7",
  "timestamp": "2026-07-28T18:21:00+08:00",
  "agent_id": "code-reviewer-v3",
  "session_id": "pr-18791",

  "output": {
    "action": "approve",
    "confidence": 0.72,
    "output_summary": "审查通过，无严重漏洞"
  },

  "input_trace": [
    {
      "source_type": "user_message|system_rule|tool_output|agent_peer|training_bias",
      "source_id": "R-0042",
      "content_hash": "sha256:abc...",
      "influence_weight": 0.0-1.0,
      "decision_path": "triggered|not_triggered|overridden"
    }
  ],

  "signature": {
    "algorithm": "ed25519",
    "agent_public_key": "abc...",
    "signed_hash": "sha256:def..."
  }
}
```

### 2.3 关键字段说明

| 字段 | 用途 | 工程要求 |
|------|------|----------|
| `decision_id` | 唯一标识，支持链式引用 | UUID v7（时间有序） |
| `input_trace[].source_type` | 区分归因来源 | 枚举值，不可自定义扩展 |
| `source_type: "training_bias"` | 关键设计 — 允许 Agent 感知并报告自己的训练偏好 | 需要模型配合，但技术上可行（RLHF 阶段的日志） |
| `influence_weight` | 影响权重 0-1 | 由 Agent 自评，审计层可交叉验证 |
| `signature` | 链上防篡改 | Agent 需要持有私钥 |

## 三、信任链传递机制

### 3.1 可传递的信任

归因链的核心优势：**每一跳的证据链都可以被下一跳验证，并带上自己的决策溯源。**

```
A Agent:  approve (附带决策溯源 JSON_A)
    ↓
B Agent:  基于 A 的输出 + 自己的判断 → 决策 (附带 JSON_A + JSON_B)
    ↓
C Agent:  { 轨迹: [JSON_A, JSON_B, JSON_C] }
```

### 3.2 审计 Agent 的独立验证

定义一个独立于业务链的**审计 Agent**，职责：

1. 收集整条决策链的溯源 JSON
2. 验证每跳的签名完整性
3. 检查归因链是否存在异常模式：

| 异常模式 | 判定规则 | 响应 |
|----------|----------|------|
| 依赖缺失 | 决策引用了某 Agent 的输出，但该输出的溯源 JSON 不可用 | 标记 "证据链断裂" |
| 权重异常 | 某条输入的 `influence_weight` 远高于实际应有水平 | 标记 "潜在操纵" |
| 规则未触发 | 决策结果与某个高优先级的 system rule 冲突 | 标记 "优先级偏离" |
| 循环依赖 | A 引用 B，B 又引用 A | 标记 "归因环路" |

### 3.3 闭环改进

当审计 Agent 发现特定 pattern 反复导致错误决策时，自动生成改进建议：

```
发现: user_message 中 "CEO特批" 模式 → agent_peer 权重 0.8 → 规则 R-0042 未触发
建议: 在 system rule 层增加规则优先级: R-0042 > user_message 中的业务特批指示
```

## 四、工程可行性分析

### 4.1 实现成本

| 组件 | 工作量 | 难度 |
|------|--------|------|
| 决策溯源 JSON 生成 | 低 — Agent 调用后附加工序 | ★☆☆ |
| 签名集成 | 中 — 需要密钥管理基础设施 | ★★☆ |
| 审计 Agent | 中 — 归因逻辑基于规则，不需大模型 | ★★☆ |
| pattern 分析 → 自动改进建议 | 高 — 需要跨 session 的模式挖掘 | ★★★ |

### 4.2 不解决的问题

| 问题 | 说明 |
|------|------|
| 训练数据中的隐性偏见 | 即使 Agent 报告了 `training_bias`，也无法保证它报告了全部偏见 |
| Agent 恶意隐瞒溯源 | 如果 Agent 故意输出虚假的 `influence_weight`，签名只能保证"没被改过"，不能保证"内容真实" |
| 审计 Agent 本身的信任 | 我们之前问的"谁审计审计者"——解决方案是审计 Agent 也要输出归因链，形成递归，在 N 层深度收敛 |

### 4.3 与现有技术的对比

| 方案 | 可追溯性 | 防篡改 | 可改进性 | 工程成本 |
|------|----------|--------|----------|----------|
| 纯日志审计 | ★★★ | ☆☆☆ | ★☆☆ | 低 |
| 行为审计 + 规则引擎 | ★★☆ | ★★☆ | ★★☆ | 中 |
| **归因链（本提案）** | ★★★ | ★★★ | ★★★ | 中高 |
| ~~动机审计（哲学方案）~~ | ☆☆☆ | ☆☆☆ | ☆☆☆ | 不可行 |

## 五、下一步

1. **原型验证** — 在 OCR 或类似 Code Review 场景中植入决策溯源 JSON
2. **格式标准化** — 定义 `source_type` 枚举值约束和 `decision_path` 值域
3. **审计 Agent MVP** — 先实现签名验证 + 规则冲突检测 + 权重异常检测三项核心能力
4. **pattern 分析引擎** — 跨 session 的归因模式挖掘与自动改进建议
